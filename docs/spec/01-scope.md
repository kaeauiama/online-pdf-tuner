# 01. スコープ・制約・マイルストーン

状態: 草案(2026-10-06)。承認状況は `../decision-log.md` を参照。

## 目的

- 他人のサイトに PDF を渡さずに、結合・分割などの日常的な操作をできるようにする。
- 日本の印刷所(東京カラー印刷、キンコーズ、アクセア等)に入稿する PDF を、Word 等で作ったものでも
  ブラウザ上でチェック・修正できるようにする。

## 利用者と対象環境

- **利用者**: 本人と、所属団体のメンバー(D-011)。DTP の専門知識がない人を想定し、
  塗り足し・トンボ等の用語解説と、手順の案内を UI に組み込む。
- **主対象**: PC のデスクトップブラウザ(Chrome / Edge を優先、Firefox は動作確認のみ)。Mac / Safari の扱いは U-10。
- スマホ: PWA として動けばよい扱いで、動作は保証しない(D-003)。

## Hard Constraints

| ID | 内容 | 担保方法 |
|---|---|---|
| HC-1 | PDF の内容を外部へ送信しない | `<meta>` CSP で `connect-src 'self'`・`form-action 'none'` 等を指定。E2E テストで「処理中の外部リクエスト 0 件」を検証する |
| HC-2 | 実行時に外部オリジンからコード・WASM・フォントを読み込まない | 依存はすべてビルド成果物に同梱。CSP の `script-src`/`font-src` を `'self'` に限定。ビルド成果物に外部 URL が含まれないことをテストする |
| HC-3 | アクセス解析・トラッキングを入れない | 依存の追加時に確認。HC-1 のテストで同時に検出する |
| HC-4 | パスワードを知らない暗号化 PDF の解除・権限制限の回避をしない | 暗号化 PDF は理由コード `UNSUPPORTED_ENCRYPTED_PDF` で止める。解除はユーザーがパスワードを入力した場合のみ |

補足: GitHub Pages では HTTP ヘッダを設定できないため、CSP は `<meta>` で指定する。
`<meta>` の CSP では `frame-ancestors` 等が効かず、ページ遷移による持ち出しも防げない。
そのため HC-1 は CSP だけに頼らず、依存を最小にすることと組み合わせて担保する。

ワーカーの扱い(D-016): 同一オリジンのスクリプト URL から直接生成したワーカーには `<meta>` の CSP が効かない。
そのため pdf.js のワーカーは blob: URL 経由で生成し、ページの CSP を継承させる。
ワーカー内からの外部通信が止まることは E2E テストで確認している。
今後ワーカーやサービスワーカー(M4)を追加するときも、同じ確認を必ず行う。

## 非目標(やらないこと)

- Word のような文章編集(段落の再流し込みを伴う編集)。誤植の部分修正は U-8 で検討する(注記 A)
- RGB → CMYK 変換と PDF/X 出力(D-008、注記 B)
- OCR、Office → PDF 変換、高圧縮(重い WASM が必要で、HC-2 とサイズの制約に反する)
- 電子署名(PAdES)の付与
- 入稿データの合否保証(チェックは目安。最終判断は印刷所の最新ガイドと校正サービスに委ねる)
- 印刷所のロゴ等を使った公式風の表示(プリセット名に社名を使うだけにとどめ、「非公式」と明記する)

### 注記 A: PDF のテキスト編集が難しい理由

PDF の文字は「文章」ではなく「字形を座標に置く命令」として記録されている。
フォントが埋め込まれていること自体は、編集を妨げる理由ではない。妨げになるのは次の4つ。

1. **サブセット埋め込み**: 文書で使った字の字形しか入っていない。新しい字が必要な修正は、同じフォントではできない
2. **レイアウト情報がない**: 段落や行の情報がないため、字数が変わっても後ろの文字が詰まらない(再流し込みができない)
3. **字形番号で記録されている**: Word が出力する日本語は文字コードではなく字形番号で書かれている。
   対応表(ToUnicode)がない PDF では、修正したい箇所を探せない
4. **フォントのライセンス**: フォントの fsType が「プレビューと印刷のみ」の場合、埋め込み先の文書の編集は許諾の範囲外になる

全角文字は字幅がそろっているため、日本語の 1 文字置換は欧文よりむしろ扱いやすい。
「白で隠して上に書く」方式は採らない。下の誤字が残り、コピーや検索で出てくるため(偽の墨消しと同じ問題)。

### 注記 B: CMYK 変換を非目標にする理由

RGB も CMYK も「装置への指示値」で、色そのものを表してはいない。

1. **変換先が決まらない**: 同じ CMYK 値でも、印刷方式・紙・インキによって出る色が変わる。オンデマンド機は機械ごとのプロファイルで変換する
2. **色域の差を埋める方法に正解がない**: RGB の鮮やかな色は、インキでは再現できない。どう収めるか(レンダリングインテント)は判断の問題
3. **3 次元から 4 次元への変換で答えが一つに決まらない**: K(墨)をどれだけ使うか、インキ総量の上限は、印刷条件によって決まる。
   黒文字が 4 色を重ねた黒になると、版ズレで文字がにじむ。これを防ぐには「文字かどうか」を判定して変換を変える必要がある
4. **PDF 全体の書き換えになる**: 画像の再圧縮(劣化)、グラデーション、透明の合成結果の違いまで扱う必要があり、商用プリフライト製品並みの規模になる
5. **結果を検証できない**: 画面は RGB で表示するため、変換が正しかったかを利用者もツールも確かめられない

変換計算そのもの(littleCMS 等)は難しくない。難しいのは、変換先の条件と判断を決めることと、
PDF を壊さずに書き換えること。正解を知っているのは印刷機を持つ印刷所なので、変換は印刷所に任せる。
出力を変えない「くすみの警告」は別に検討する(U-9)。

## 技術スタック

Vite + TypeScript。PDF の書き込みに `@cantoo/pdf-lib`、描画と解析に `pdfjs-dist`(D-015)。
PWA には vite-plugin-pwa を使う(M4)。テストは Vitest(単体)と Playwright(E2E。インストール済みの Edge を使う)。
