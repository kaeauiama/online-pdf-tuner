# AI による画像の高解像度化(構想)

状態: 構想(2026-10-07)。実装していない。U-15。ユーザー要望「解像度が低い点については、今の時代なので AI Upscaling の機能が統合できると面白そう。
BYOK などとりあえず構想だけ立ててみてほしい」。

## 何を解決するか

入稿チェックで「解像度がかなり低い画像」(`PRINT_IMAGE_LOW_DPI`)や「推奨より低い画像」が出たとき、元の高解像度の画像が手元にないことがある
(Web から拾った写真、スマホの縮小済みの写真、Office が保存時に圧縮した画像)。AI の超解像で 2〜4 倍に拡大し、印刷でのぼやけ・ギザギザを目立たなくする。

## 前提(Hard Constraints との関係)

- **HC-1(PDF の内容を外部へ送信しない)**: クラウドの API に画像を送る方式(BYOK を含む)は、そのままでは HC-1 に反する。
  画像は PDF の内容そのものであり、利用者が自分のキーを使っていても「外部へ送信する」ことに変わりはない
- **HC-2(外部からコード・WASM を読み込まない)**: ブラウザの中で動かす場合も、モデルと実行環境は同梱する必要がある
- **CSP**: いまは `connect-src 'self'` で、ブラウザ自身に外部通信を禁止させている。外部の API を許すと、この保証(「送信していないことを確かめられる」)が
  サイト全体で弱まる

## 方式の候補

### A. ブラウザの中で動かす(推奨)

- ONNX Runtime Web(WebGPU、なければ WASM)で、超解像のモデルを同梱して動かす。外部通信なし。HC-1・HC-2 を満たす
- モデルの候補(ライセンスと大きさを要確認):
  - Real-ESRGAN 系の軽量モデル(realesr-general-x4v3 など。数 MB。BSD-3-Clause の配布物あり)
  - Swin2SR などの Transformer 系(高品質だが重い)
  - イラスト向け(waifu2x 系)は写真には向かないので、用途で選ばせるか、写真向けに絞る
- 大きな画像は 128〜256px のタイルに分けて処理し、境界を重ねて継ぎ目を消す
- 速度の目安(要計測): WebGPU のある PC で、1000 × 700px を 2 倍にするのに数秒〜十数秒。WASM のみだと数倍〜十倍遅い
- 同梱するモデルとランタイムで配信物が数 MB〜十数 MB 増える。最初は使うときに同じオリジンから読み込む(Service Worker で保存)

### B. 利用者の PC で動かしている外部のツールに渡す(localhost)

- Upscayl や ComfyUI などを利用者が自分の PC で起動し、そこへ画像を渡す。通信は PC の中で完結する
- CSP に `connect-src http://localhost:*` を足す必要があり、「外部へ通信しない」の説明が複雑になる。導入の手間も大きい
- 利用者が限られるため、A が使えない事情が出たときの代替として残す

### C. BYOK でクラウドの API を使う(非推奨)

- 利用者が自分の API キー(Replicate・fal・Stability など)を入れ、画像を送って高解像度化する
- HC-1 の例外になる。採る場合の最低限の条件(案):
  1. 既定はオフ。画像ごとに、送る画像と送り先を示して同意を得る(一括の同意にしない)
  2. 本体とは別のページ(別の CSP)に分け、本体の「外部へ通信しない」の保証を弱めない
  3. API キーは保存しないか、保存する場合もこの PC のブラウザの中だけ。PDF そのものは送らず、対象の画像だけを送る
  4. 送信の記録(何を・どこへ)を画面に残す
- 所属団体のメンバー(DTP の知識がない人)に、送信のリスクを正しく判断してもらうのは難しい。本ツールの出発点(他人のサイトへの不信)とも合わない

## 使い方の案(A の場合)

1. 入稿チェックの解像度の指摘に「AI で高解像度にする(試験的)」を出す
2. 対象の画像ごとに、拡大率(2 倍 / 4 倍)と、元の画像・結果の比較(拡大表示で切り替え)を示す
3. 利用者が「この画像を置き換える」を選んだものだけ、PDF の画像を差し替える(新しい版として並びに入れ、元に戻せる)
4. 入稿チェックでは、置き換えた画像を「AI で補完」と表示し、解像度の指摘の代わりに注意を出す

## 注意(利用者に示すこと)

- AI は「ありそうな細部」を描き足す。人の顔・文字・ロゴ・細かい模様は、元と違う形になることがある。必ず拡大して確かめる
- 解像度の数値は上がっても、元にない情報は戻らない。大きく引き伸ばすほど不自然になりやすい
- 透明部分(SMask)を持つ画像は、マスクも同じ倍率で拡大する必要がある

## 進め方(案)

| 段階 | 内容 |
|---|---|
| P0 | スパイク: ONNX Runtime Web + 小さなモデルで、ブラウザの中で 2 倍の拡大が動くか、速度とメモリ、モデルのライセンスを確かめる |
| P1 | 入稿チェックからの 1 画像ずつの置き換え(比較表示・元に戻す) |
| P2 | タイル処理と進捗表示、SMask の拡大、複数画像の一括処理 |

## 決めること(U-15)

- A(ブラウザの中)で進めるか。配信物の大きさの増加(数 MB〜)を許容するか
- B・C を将来も含めて採らないか(採るなら、HC-1 の例外としての条件を先に決める)
- モデルの選定(写真向けに絞るか、イラスト向けも入れるか)
